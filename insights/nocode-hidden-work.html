노코드로 만드는 것은 반나절이지만 굴리는 것은 그다음부터입니다

노코드 강의는 만드는 쾌감을 팝니다. 운영하고 유지보수하는 방법은 가르치지 않습니다. 도구를 굴리는 숨은 작업입니다.

5분 읽기Full Insight
  • 소프트웨어 생애 비용의 60-80%는 개발이 아닌 유지보수에 쓰입니다. 노코드는 만드는 속도를 높이지만 이 비율을 바꾸지 않습니다.
  • 노코드 강의가 가르치지 않는 것은 외부 API가 바뀌었을 때, 데이터가 예상과 다르게 들어왔을 때, 원래 만든 사람이 팀을 떠났을 때 무엇을 하는가입니다.
  • 노코드 도구의 생애 주기를 만들기 단계에 포함하지 않으면, 관리되지 않는 도구가 빠르게 쌓입니다.

만드는 것과 굴리는 것은 다른 문제입니다

소프트웨어 공학 연구들은 수십 년 동안 일관된 관찰을 보고합니다. 소프트웨어 생애 비용의 60-80%는 초기 개발이 아닌 유지보수에 쓰인다는 것입니다. Ian Sommerville의 소프트웨어 공학 교과서가 여러 판을 거쳐 인용하는 수치이며, 다수의 산업 연구가 같은 범위를 보고합니다. 노코드 도구는 만드는 속도를 높이지만 이 비율을 바꾸지 않습니다.

노코드로 영업 자동화 도구를 이틀 만에 만들었습니다. 처음 두 달은 잘 작동했습니다. 세 달째에 연동한 외부 서비스가 API를 업데이트했습니다. 도구가 작동을 멈췄습니다. 원래 만든 사람이 방법을 찾았지만 두 시간이 걸렸습니다. 여섯 달째에 그 사람이 퇴사했습니다. 도구는 남아 있지만 관리할 사람이 없습니다. 팀은 다시 수동으로 돌아갔습니다.

이것이 노코드의 숨은 작업입니다. 만드는 과정에서는 보이지 않고 굴리기 시작한 뒤에야 나타납니다. 강의는 만드는 단계까지만 다룹니다.

노코드 강의가 가르치지 않는 것들

외부 API 변경에 대한 대응입니다. 노코드 도구는 대부분 외부 서비스와 연동됩니다. Zapier, Make, n8n 같은 자동화 플랫폼은 각 앱의 API를 중개합니다. 외부 앱이 API를 변경하면 자동화가 멈춥니다. 강의에서는 연동을 설정하는 방법을 가르칩니다. 연동이 끊겼을 때 진단하는 방법은 가르치지 않습니다.

데이터 예외 처리입니다. 도구를 만들 때는 데이터가 예상한 형식으로 들어온다고 가정합니다. 실제 운영에서는 예상하지 못한 형식의 데이터가 들어옵니다. 빈칸, 중복, 잘못된 형식의 날짜, 예상 범위를 벗어난 숫자입니다. 이 예외를 처리하는 로직을 처음부터 설계하지 않으면 도구가 예외를 만날 때마다 멈추거나 잘못된 결과를 냅니다.

운영 지식 이전입니다. 노코드 도구는 만든 사람만 구조를 압니다. 문서화하지 않으면 그 사람이 팀을 떠날 때 도구의 운영 지식도 함께 사라집니다. 코드로 만든 시스템에는 코드가 남아 있습니다. 노코드 도구에는 UI 설정만 남아 있어서 다른 사람이 구조를 파악하기 더 어려울 수 있습니다.

도구 생애 주기를 만들기에 포함하는 방법

노코드 도구를 만들기 전에 다음 세 가지를 먼저 결정합니다. 첫째, 이 도구를 굴릴 담당자가 만든 사람 외에도 있는가입니다. 담당자가 한 명이면 그 사람이 떠날 때 도구도 멈춥니다. 둘째, 연동한 외부 서비스가 API를 바꿀 때 알림을 받을 방법이 있는가입니다. 대부분의 서비스는 API 변경 공지를 이메일이나 개발자 채널로 보냅니다. 셋째, 도구를 언제 없앨지를 처음부터 결정해 두는가입니다.

가트너의 시민 개발 연구는 노코드 도구의 생애 주기 관리가 단일 도구가 아닌 포트폴리오 관점에서 이루어져야 한다고 권고합니다. 도구 하나씩 관리하면 어느 도구가 살아 있고 어느 도구가 작동하지 않는지 파악하지 못합니다. 조직 내 모든 노코드 도구를 목록화하고 각 도구의 상태와 담당자를 주기적으로 확인하는 체계가 필요합니다.

Ahn Partners 판단: 노코드의 가치는 부정하지 않습니다. 개발팀 없이 현장 문제를 빠르게 해결하는 능력은 실제로 유용합니다. 그러나 노코드 도구를 도입하는 동기가 '빠르게 만들 수 있다'는 것에만 있으면, 굴리는 비용이 예상보다 훨씬 크게 나올 수 있습니다. 만들기가 쉬울수록 관리되지 않는 도구가 더 빠르게 쌓인다는 점이 핵심입니다.

언제 굴리고 언제 버릴 것인가

노코드 도구의 지속 조건은 세 가지입니다. 담당자가 만든 사람 외에 최소 한 명 더 있을 것. 도구가 사용하는 외부 서비스의 변경 공지를 받는 체계가 있을 것. 도구의 사용량과 오류 발생 빈도를 월 단위로 확인하는 사람이 있을 것입니다.

이 세 가지 중 하나라도 없으면 그 도구는 관리되지 않는 상태입니다. 관리되지 않는 도구는 정리하는 것이 맞습니다. 작동하는 것처럼 보이지만 실제로는 잘못된 결과를 내고 있을 수 있고, 연동이 끊겼을 때 아무도 알아채지 못할 수 있습니다.

이번 주에 점검할 것은 지금 팀에서 쓰고 있는 노코드 도구 목록입니다. 각 도구마다 지속 조건 세 가지를 확인합니다. 조건을 충족하지 못하는 도구는 담당자를 지정하거나 폐기를 결정합니다.

점검 목록

  • 현재 팀에서 운영 중인 노코드 도구 목록이 있으며, 각 도구의 담당자와 상태가 기록되어 있는가
  • 각 도구가 연동하는 외부 서비스의 API 변경 공지를 받는 체계가 있는가
  • 노코드 도구를 만들 때 운영 담당자, 유지보수 방법, 폐기 기준을 먼저 정하는 절차가 있는가
